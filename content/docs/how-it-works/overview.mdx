## Summary

Rós Madair compiles Arches (alizarin) graph data into a **DuckDB + Parquet
substrate** that is served from a CDN or static host and queried without a
backend database. A reader compiles the typed query IR to DuckDB SQL, prunes row
groups on the Parquet zone-map, fetches only those via HTTP Range, filters
exactly, and hydrates the matches into a schema-shaped tree.

## See it, piece by piece

Each capability below has a live, in-browser demo — running the **same compiled SQL
the native reader runs**, over duckdb-wasm:

- **[Querying](/docs/live-query)** — a `Concept` + `Range` + `Bbox` IR lowered to SQL, pruned on the zone-map.
- **[Hydration](/docs/tile-store)** — query results rehydrated into rich, typed alizarin resources, link resolution and all.
- **[The round trip](/docs/roundtrip)** — alizarin builds a concept-hierarchy query and receives typed resources back; Rós Madair is only the middle.
- **[Layers](/docs/layers)** — a base snapshot plus a sparse overlay, composed at query time.
- **[Verification](/docs/verification)** — a signed snapshot, verified (or refused) at open.

Then **[see it on Aonach Mór](/docs/aonach-mor)** — the whole thing end to end on a resilience corpus.

## The pipeline

```
alizarin graphs + resources + vocabularies (a data_dir)
        │  ros-madair-emit   (CLI)
        ▼
  tiles_<graphid>.parquet  tile = row; only geo_* promoted, its row-group min/max stats
                           ARE the spatial zone-map; `data` = hydration JSON
  concepts_<graphid>.parquet  melted node-keyed concept store (Concept = a node-scoped semijoin)
  ordered_<graphid>.parquet   melted node-keyed ordered-scalar store (Range = a node-scoped read)
  edges_<graphid>.parquet  one row per link target — HasLink / OnLink / cited_by semijoin this
  concept_catalog.parquet  concept DFS intervals (hierarchy = a range join)
  manifest.json            layout + FORMAT_VERSION contract; signed snapshot_id
        │  ros-madair-duck (native) / DuckDB-WASM (browser)
        ▼
  compile the Query IR → DuckDB SQL (zone-map prune → exact filter, over HTTP Range)
  → hydrate matches into a schema-shaped JSON tree (overlay + cited_by aware)
  → verify the manifest signature before trusting a snapshot
```

## The artifacts

- **`tiles_<graphid>.parquet`** — one row per tile. A field's storage class is a
  pure function of its datatype (`ros-madair-handlers`): concepts and ordered
  scalars (dates/numbers) are **melted** into their own node-keyed stores
  (below), geometry → `geo_*` promoted onto the row, everything else → the
  `data` JSON blob for hydration. Only `geo_*` is promoted, and its per-row-group
  min/max stats in the Parquet footer **are** the spatial zone-map — no separate
  index.
- **`concepts_<graphid>.parquet`** and **`ordered_<graphid>.parquet`** — the
  melted node-keyed stores (one row per resource/tile/nodegroup/node/value). A
  `Concept` filter compiles to a node-scoped semijoin over the concept store; a
  `Range` is a node-scoped read over the ordered store — so concepts and dates
  live off the tile row, not as promoted columns on it.
- **`edges_<graphid>.parquet`** — one row per link target; `HasLink`, the `OnLink`
  **multi-hop path predicate**, and `cited_by` reverse traversal all semijoin this
  columnar edge table. Chained `OnLink`s walk the graph hop by hop — *person →
  employer → occupied building → exposure → hazard footprint* — the deep multi-hop
  queries that distinguish Rós Madair from a flat table scan, each hop a node-scoped
  semijoin that prunes as it goes.
- **`concept_catalog.parquet`** — concept DFS intervals, so a hierarchy query
  (`DescendantOrSelfOf`) is a range join.
- **`manifest.json`** — the layout + `FORMAT_VERSION` contract, carrying a signed
  `snapshot_id`. A reader refuses a version it does not implement, and verifies
  the attestation before trusting the snapshot ([Verification](/docs/verification)).

## The read path

`ros-madair-query` defines the typed IR (`Concept`, `Range`, `Bbox`, `HasLink`,
`OnLink`, `OnTile`) — plus `ModelCatalog` (a discovery surface for NL→IR
authoring) and `explain` (IR → English). It is backend-agnostic. `ros-madair-compile`
is the one pure IR → DuckDB SQL compiler (`compile_expr`/`compile_query`, no
libduckdb, builds for `wasm32`); it has two consumers — `ros-madair-duck`
executes the SQL natively, and `ros-madair-wasm` (npm `ros-madair`) runs the same
lowering in the browser over duckdb-wasm. `ros-madair-duck`:

- **compiles** the IR to DuckDB SQL over Parquet (via `ros-madair-compile`) and
  **resolves** it to resource ids (row-group prune, then exact filter — including
  exact `ST_Intersects` where the spatial extension is available);
- **hydrates** matching tiles into a schema-shaped tree;
- composes **layered overlays** (a base plus on-device overlays, precedence per
  resource + nodegroup), across which an `OnLink` hop can traverse;
- answers **reverse traversal** (`cited_by`); and
- **verifies** each layer's signed content, refusing a tampered snapshot.

## Direction: DuckDB + Parquet

The coarse/fine head+chunk read engine that used to sit here has been **replaced**
by this substrate — it was a reimplementation of what Parquet zone-maps + DuckDB
give natively (and, for spatial, a less complete one). What is genuinely
RM-specific is kept: layered overlay, reverse traversal, tile-graph hydration,
and snapshot signing. Full-text search stays with a separate inverted index
(Pagefind), because zone-maps have no order to prune text on.

See the
[README's Direction section](https://github.com/flaxandteal/ros-madair#direction-duckdb--parquet-substrate)
for the findings, the tile-row Parquet layout, nodegroup partitioning and
hierarchical ordering, egress governance, and the roadmap. The DuckDB-WASM
browser runtime has since landed — `ros-madair-compile` builds for `wasm32` and
`ros-madair-wasm` (npm `ros-madair`) wraps it, so a browser page compiles the same
SQL the native reader runs; the remaining work is repointing the last docs demos.
